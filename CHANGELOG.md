## 1.4.1 — 2026-11-02

### Added
- **Work across several repositories.** The agent knows every repository in reach: the folders of a multi-root workspace, those in the workspace's `.localpilot/repos.json`, and the `localpilot.repos` setting. The new `repos` tool lists them with branch and changes, searches all of them, and runs one command in several (asking once). For a change that spans repositories, `run_parallel_subagents` takes a `repo` per task, and that subagent works inside its repository with every tool, including git and pull requests. Files in registered repositories can also be read and edited directly (`../api/server.js`). With Gemma 4 12B, "make the API listen on 4000 and update the web app to call it" changed both repositories correctly. Also fixed: an absolute path inside a repository nested in another workspace folder was redirected as if it were outside. See [Several repositories](docs/docs/parallel-agents.md#several-repositories).
- **Shared task board for teams and agents.** `.localpilot/board/` holds one Markdown file per task (state, priority, dependencies, owner, brief, handoff notes, result), so the board is committed and reviewed with the code. The agent manages it with the `team_board` tool (list, add, claim, note, complete, fail, release); `localpilot work` (or **LocalPilot: Work on Shared Board**, once per worker) keeps taking the next free task until none is left, and several workers split the board between them. Claims are made under an exclusive lock so two workers never take the same task, and hold a lease renewed while working, so a crashed worker's task is taken over and the takeover noted. Only a task's owner can close it; anyone can leave a note. `/board` shows it in the chat. Tested with two Gemma 4 12B workers on three tasks: they split the independent ones and the dependent one ran after both. See [The shared board](docs/docs/parallel-agents.md#the-shared-board).
- **Remote MCP servers.** An MCP server can now be a URL as well as a command. LocalPilot speaks Streamable HTTP (JSON or event-stream replies, server sessions, the negotiated protocol version on every request) and the older HTTP+SSE transport, chosen from `type` or the URL, and falls back from HTTP to SSE when an older server refuses the first. `headers` (with `${env:…}` / `${secret:…}`) carry authentication. Configure them in **Settings → MCP servers** (paste a URL instead of a command), in `localpilot.mcpServers`, or in a plugin's `.mcp.json` in Claude Code's format. Checked against DeepWiki's public server: connected over Streamable HTTP, and Gemma 4 12B answered a question with its tool in one call. See [MCP servers](docs/docs/mcp.md#remote-servers).
- **Agent benchmark.** `localpilot eval` (or **LocalPilot: Run Agent Benchmark…** in VS Code) runs real coding tasks with the actual agent loop, each in a fresh temporary workspace, and checks every result by running it: the task's tests, a command, file contents or the answer. The built-in suite has eight tasks (bug fixes, implementing from tests, a multi-file rename, a signature change with its callers, a precise config edit, two codebase questions); every one fails as shipped and passes with a reference solution. The report compares models on pass rate, time, steps, tool calls, tool errors and tokens, shows the change since the last run, and lists why each task failed. Projects add their own suites in `.localpilot/evals/*.json`. It exits with 1 on a failure, so CI can gate on it. First result on this machine: Gemma 4 12B passed 3 of 8; the failures were mostly timeouts after repeated empty replies and stalls from the model, which is now measurable. See [Benchmarking models](docs/docs/terminal-and-cli.md#benchmarking-models).
- **Pull requests and CI from the chat.** `/pr` commits the current changes on a new branch (after running the checks that cover them), pushes and opens a pull request with a description; `/fix-ci` reads the failing GitHub Actions checks, reproduces the failure, fixes it and pushes. The agent also has the tools behind them: `git_status`, `git_commit`, `git_push` (never forced, refuses the default branch unless you ask), `pull_request` (create, view, list, comment) and `ci_status` (runs, the log lines of failed steps, re-run). Pull requests and CI use the GitHub CLI. Commits ask like edits, pushes, comments and re-runs like terminal commands, and in Ask and Plan mode only the reading actions are available. With Gemma 4 12B, "commit my change on a new branch and push it" produced the branch, a conventional commit and the push in one run.
- **Organization policy.** Administrators can deploy `managed-settings.json` to a system location (`/Library/Application Support/LocalPilot/` on macOS, `/etc/localpilot/` on Linux, `%ProgramData%\LocalPilot\` on Windows), and users and projects cannot override it. It can always block or always ask for actions (same rule syntax as `settings.json`), set an approval floor per kind of action, turn off bypass modes and Auto mode, cloud providers (or allow only listed hosts), web access, MCP servers not on a list and skill downloads, and write every tool call and approval to a JSON Lines audit log. A policy that cannot be parsed fails closed. Users see it in Settings, `/permissions` and `localpilot doctor`. Also fixed along the way: an `ask` rule on a tool that never prompts by itself (`Read(.env)`) let the call run without asking; it now asks. See [Organization policy](docs/docs/configuration.md#organization-policy).
- **Repository graph.** A new `repo_graph` tool builds an import graph and a symbol index straight from the source (TypeScript/JavaScript, Python, Go, Rust, Java/Kotlin, C#). It needs no language server, so it works in the CLI too, and it re-reads only changed files: this repository's 144 files index in 38 ms. Ask "what breaks if I change `src/util.ts`?" and the agent lists every file that imports it, directly or through others, and the tests to run. It also finds where a symbol is defined, the most-imported modules, import cycles and which files use a package. With Gemma 4 12B, an impact question that a text search answered wrongly (one file found, "no tests") is now answered correctly in one tool call. See [Context](docs/docs/context.md#repository-graph).

## 1.4.0 — 2026-11-02

### Added
- **Every setting is in the Settings page.** Auto mode (and its reviewer model) and how many queued tasks run at once are under Agent & approvals; the memory note limits under Memory; keeping Ollama and Redis running and installing Ollama without asking under Advanced → Background services; the LiteLLM config file under Providers → Gateways. Search finds them, along with skill and plugin folders and hidden models.
- **The task queue is part of the extension API** (`queue.add`, `list`, `cancel`, `retry`, `remove`, `setPaused`, `onDidChange`), so scripts and other extensions can queue agent tasks with dependencies.

### Changed
- **Version numbers carry over after 9.** Each part counts 0–9: the release after 1.3.9 is 1.4.0 (not 1.3.10), and after 1.9.9 it is 2.0.0. The next release after the current 1.3.11 is 1.4.0.

### Fixed
- **Changing providers takes effect at once.** A model listing that was still running when you added, removed or edited a provider finished afterwards and put the old providers' models back for up to 30 seconds. Agents started in that window (a parallel batch, Best of N, queued tasks) could be sent to a provider that was no longer configured and fail with "Provider … not configured". Results from before the change are now dropped and the current providers are listed.
- **A provider added while LocalPilot starts is no longer lost.** Startup detection probes local ports and Docker for a few seconds, then saved the provider list as it was when it began, which dropped a provider added meanwhile (in Settings, by Start Gateway or by setup). It now adds what it found to the list as it is at that moment.

## 1.3.10 — 2026-11-02

### Fixed
- **Auto never sends code to the cloud while a local model can do the job.** On a machine with little memory (8 GB or less), a local model that only just fits lost its memory points, while a cloud model, which needs no memory here, gained them. That was enough to cancel the cloud penalty, so Auto could pick Claude or a gateway over the local model. Auto now chooses among local models first and uses a cloud model only when there is no usable local one; choosing a cloud model yourself works as before.
- **Start colibri finds a checkout in `~/colibri` on every platform.** The default folder was joined with the separator of the machine running the check rather than the target platform's.

## 1.3.9 — 2026-11-02

### Fixed
- **Context sizes are measured, not guessed.** Token counts came from a character-based estimate that was far off on real models: on Gemma 4 it was 30% low for code and 42–77% high for prose and the agent's own instructions. So the context meter was wrong, and compaction started too late on code-heavy chats and too early on the rest. Every model server reports the real prompt size after each request; LocalPilot now uses it to calibrate its estimates for that model, so the meter and the compaction point follow the real numbers. The meter also updates during a run (before each request, after each reply and after compaction) instead of only when the turn ends.
- **Compacting by hand can no longer lose your conversation.** When the summary could not be made (the server was down, the model not loaded, or it returned nothing), clicking the context meter or running `/compact` replaced the older messages with a one-line "was truncated" note. It now leaves the chat as it was and says why. It also shows that it is working, ignores a second click while it runs, and keeps the system prompt and tools in the meter's count afterwards.
- **"Remember …" saves to LocalPilot's memory.** Asking the agent to remember something could install a catalog skill named "remember" that keeps notes somewhere LocalPilot never reads, and with Gemma 4 the run then failed with empty replies. Requests to remember or forget something now go straight to the built-in memory tools, and the next chat starts with them.
- **Memory stays within its share of the prompt.** The index of saved notes was added to every system prompt in full, however many notes there were. It now takes about 5% of the context window (1,500 to 12,000 characters); notes that do not fit are counted, and `memory_list` still shows them all.
- **Turning memory off turns it off.** With `localpilot.memory.enabled` off, the agent was still offered the memory tools and told to save notes, which were then never read. Now it is not.
- `/memory` lists the saved memory notes as well as the instruction files (CLAUDE.md, AGENTS.md…).

## 1.3.8 — 2026-11-02

### Added
- **Start colibri installs, configures and starts colibri.** It handles every starting point:
  - **Not installed:** after checking for git and Python, it clones colibri and runs colibri's own setup in a terminal. You choose the folder (default `~/colibri`) and a model ranked for this machine (runs from RAM, streams from disk, or too big), with a free-disk check. Setup builds or downloads the engine, downloads the model and starts the server.
  - **Installed but not set up:** colibri recommends a model and sets up without questions.
  - **Set up:** it just starts, with no download or build.
  - **Already running:** it reuses the server and offers **Switch model…**, **Stop colibri** and **Open dashboard**.
  - **Another server on the port** (vLLM also uses 8000): it offers the next free port.

  colibri is found as a configured checkout or release, `coli` on PATH, or `~/colibri`. A Windows source checkout runs with `py -3`. KV slots for parallel agents are passed through `COLI_KV_SLOTS`. The progress notification shows colibri's install phase and percentage, and waits as long as a large download needs. Cancelling never stops colibri. New: **LocalPilot: Stop colibri**, and the `localpilot.colibri.modelsDir` and `localpilot.colibri.backend` settings.
- **Start Gateway runs OmniRoute or LiteLLM end to end.**
  - **Starting:** it adds the gateway as a provider marked cloud, reuses one that is already running, moves to a free port if something else holds it, and starts it in a terminal bound to 127.0.0.1. OmniRoute's own default is every network interface.
  - **Installing:** OmniRoute installs with `npm install -g omniroute` after a Node.js version check. LiteLLM installs with pip, and Start Gateway asks once for its config file.
  - **No provider connected:** a fresh OmniRoute lists only its `auto` routes. Start Gateway says so and offers **Open dashboard** and **Refresh models**.
  - **No route in chat:** a "no eligible route" reply reads "the gateway has no provider it can send this request to", says where to fix it, and isn't retried.
  - **Also:** **Start** buttons on the gateway provider cards, and **LocalPilot: Stop Gateway**.
  - **Checking a real gateway:** `npm run e2e:gateway` drives the CLI through a running gateway, including a real tool call.

## 1.3.2 — 2026-11-01
### Added
- **Cloud model providers.** **Settings → Providers** now lists cloud APIs next to local servers: OpenAI, Anthropic (Claude), Google Gemini, OpenRouter, Groq, Mistral, DeepSeek, xAI, Together, Fireworks, Cerebras, Hugging Face, NVIDIA NIM, Moonshot, Alibaba Qwen, Azure OpenAI and Ollama Cloud. Claude uses a new `anthropic` provider type that talks to the Messages API directly, with tools and images. The other clouds use the OpenAI-compatible API. Cloud providers are marked **cloud**. Auto and other automatic picks still prefer local models and use a cloud model only when nothing local is available. A cloud model you choose yourself is always used.
- **API keys stay out of settings.json.** A key pasted into a provider card is stored in VS Code secret storage (your OS keychain); settings.json keeps only `${secret:<id>}`. **LocalPilot: Set Provider API Key…** does the same from the Command Palette. A key can also be read from an environment variable with `${env:NAME}`; cloud presets use the provider's usual variable (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`…). **Test connection** names a variable or stored key that is missing. The CLI reads `LOCALPILOT_KEY_<ID>` for keys kept in secret storage.
- **Claude thinking, tool loops and prompt caching.** Claude models think according to `localpilot.thinking`: adaptive thinking with an effort level on Claude 4.6 and later, a token budget on older models. Reasoning is streamed to the chat and sent back with its signature during the tool loop that produced it. If a pruned or compacted history makes the API reject it, LocalPilot resends once without it. Prompt caching is on.
- **OmniRoute and LiteLLM gateways.** Presets for [OmniRoute](https://github.com/diegosouzapw/OmniRoute) (`localhost:20128`) and LiteLLM (`localhost:4000`), and auto-detect finds both. They run locally but forward prompts to cloud models, so they are marked as cloud and automatic picks keep preferring local models. Mark any other local proxy the same way with **Sends prompts to cloud models** (`"cloud": true`).
- **More local presets:** KoboldCpp, text-generation-webui and GPT4All.
- **Cloud providers in the CLI.** `localpilot providers` lists local and cloud providers with reachability and key state. The other subcommands:
  - `providers presets` lists what you can add.
  - `providers add <preset|url>` adds one and checks the connection. It asks for a missing cloud key without echoing it, or takes `--key` / `--key-env`.
  - `providers key <id>` sets, replaces or removes a key, given as an argument, typed or piped in.
  - `providers test` checks one provider or all of them.
  - `providers remove` removes a provider.

  Providers added in the terminal join the ones from VS Code by id; VS Code's settings are never written. Keys the editor keeps in the OS keychain are read from `~/.localpilot/keys.json` (owner-only) or `LOCALPILOT_KEY_<ID>`. `localpilot models` and `doctor` mark cloud models, and `/providers` works in a session.

### Fixed
- **The first-run setup page fits narrow panels.** Long server addresses no longer push it wider than the panel at sidebar widths.
- **Settings fit narrow panels.**
  - Provider and MCP server names are no longer cut to a few letters; status badges move under the name instead.
  - The **New MCP server** fields and the **Find a provider** filter each get their own row.
  - Memory notes show as small cards instead of a clipped table.
  - Dashboard charts no longer overflow at 300 px.
- **Cloud models that reject a parameter now work.** OpenAI reasoning models don't accept `temperature` or `max_tokens`, and some APIs don't accept `reasoning_effort`. LocalPilot now drops or renames the parameter, asks again and remembers this for that model. Context windows and vision support are filled in for well-known cloud models whose listing omits them. Speech, image and embedding models are hidden from the pickers.
- **Cloud rate limits are waited out properly.** On HTTP 429 the agent now waits as long as the provider asks in `retry-after`, or 5 s then 10 s when it doesn't say, at most 60 s. It used to wait 0.8 s and 2.5 s, which cloud APIs reject again.
- **A rejected API key or an exhausted quota is reported at once.** It used to be retried. The message says what happened and where to set the key: OpenAI's `insufficient_quota` and Anthropic's "credit balance is too low" read as "out of credits or quota", a 401/403 as "rejected the API key".
- **Ghost text works with a cloud model you choose for it.** Cloud APIs have no `suffix` completion endpoint, so LocalPilot sends the code around the cursor through chat and inserts only the reply. Claude also sees the code after the cursor now.
- **Cloud models are labelled everywhere.** They now show "cloud" in Settings → Models and in VS Code's language-model list for other extensions, along with vendor marks for Claude, OpenAI and xAI models.
- **Ollama `*-cloud` models are no longer counted against local memory.** Model management (pull, remove, start Ollama) uses only a local Ollama, never Ollama Cloud.
- **Cloud models are never warmed up or auto-tuned.** Warming a cloud model would only cost tokens. Auto-tune never writes a cloud model into your settings.

## 1.3.1 — 2026-10-31
### Fixed
- **A reply that is all thinking no longer stalls the agent.** A reasoning model could spend its whole reply budget thinking and never answer. LocalPilot then repeated the identical request, which did the same again, costing minutes. It now asks again with thinking turned off and keeps it off for the rest of that turn.
- **Thinking levels follow what Ollama supports.** Ollama takes `low` / `medium` / `high` only for gpt-oss. For other thinking models, Auto's light thinking (Ask, subagents) now means no reasoning pass, and medium or high means the model's normal thinking.

## 1.3.0 — 2026-10-31
### Added
- **Questions before the agent starts.** For a new feature or an open-ended, larger request, the agent first looks at the code. Then it asks up to four questions in one card in the chat. Each option explains what choosing it means, one is marked **Recommended**, some allow several picks, and you can always answer in your own words. After that it states a short plan and builds. Clear, specific requests start right away. **Skip** (or Esc) lets it go with its recommendations. Use the keyboard: 1–9 to pick, Enter to submit. Choose how often it asks in `localpilot.clarify.questions`: `smart` (default), `interview` (also waits for your OK on the plan) or `minimal`. Queued tasks never stop to ask. In the CLI, questions appear in the terminal.
- **Thinking chosen per task.** `localpilot.thinking` now defaults to `auto`: more reasoning for Plan and Debug, medium for the agent and Multitask, light for Ask and subagents, and none for quick helpers (the Auto-mode reviewer, inline edits, compaction summaries) so they stay fast. `off` now really turns thinking off; before, thinking models reasoned anyway. Models that cannot think are never sent the option.
- **Task queue.** **LocalPilot: Queue Agent Task…** (or **+** on the new **Queue** section of the Agents view) lines up agent tasks. Each task has its own mode and model, and can wait for other tasks to succeed first. Tasks run one after another by default. Set `localpilot.queue.concurrency` to run several side by side, each in its own worktree. When a task fails, the tasks that depend on it are blocked rather than run, and **Retry** puts them all back in line. The queue is saved per workspace and resumes after a reload. You can pause and resume it.
- **Auto mode.** With **LocalPilot: Toggle Auto Mode** on (⚡ in the status bar), an action that would ask for approval is first reviewed by a small local model. The reviewer approves actions that clearly serve your request and stay inside the project. Everything else still asks you. Pushes, `sudo`, recursive deletes, piping a download into a shell, publishing, infrastructure changes and writes to secrets or `.git` always ask. The reviewer can only approve, never deny, and any reviewer error falls back to asking. Settings: `localpilot.autoMode.enabled`, `localpilot.autoMode.model`.
- **Background services.** LocalPilot keeps a local Ollama running while VS Code is open, once Ollama has run in the session or serves the default model. It also keeps Redis running when Redis storage is on, using its Docker container or a native `redis-server`. Failed restarts back off, and after four in a row LocalPilot stops trying and tells you. **LocalPilot: Show Background Services** shows each service's state. Opt in to `localpilot.supervisor.autoInstall` to install Ollama and a starter model without being asked when no model server is found.
- **Memory limits.** Appending to a memory note skips lines it already has. A note over `localpilot.memory.maxNoteChars` (8000) loses its oldest paragraphs, and past `localpilot.memory.maxNotes` (200) per scope the least recently updated notes are removed (`README` is kept). The agent is told what was trimmed.
- **Improve prompt.** The sparkle button in the composer (or ⌘I / Ctrl+I) has the chat's model rewrite your draft into a precise request. It names the actual file, function or selection behind "this" or "it", fixes spelling and expands shorthand. It never adds requirements, keeps questions as questions and never starts the task. The rewrite streams into the composer for you to review. Nothing is sent, and ⌘Z / Ctrl+Z brings your original back.
- **Misspelled names in requests are corrected.** File names and code identifiers you mistype are matched to the real names in the workspace before the agent starts (`dicee.py` → `dice.py`, `rollDise` → `rollDice`), so its first search or read hits the right target. Plain words, URLs and `@mentions` are never changed. A file name is only corrected to one with the same extension, and a name with two equally close matches is left alone. The correction is shown under your message. Setting: `localpilot.prompts.autoCorrect`.
- **Ollama server tuning.** `localpilot.ollama.flashAttention` (on) and `localpilot.ollama.kvCacheType` (`q8_0`) apply when LocalPilot starts or restarts Ollama. A q8_0 KV cache uses about half the memory of f16, so large context windows load faster and stay on the GPU.

### Fixed
- **Auto picks the stronger model again.** Auto gave a name-based bonus only to Gemma 4 and Nemotron, so a smaller Gemma 4 outranked a bigger model with the same capabilities (for example `gemma4:12b` over `qwen3.8:27b` on a 36 GB Mac). Any model that calls tools and reads images now counts as frontier-class, so the bigger one wins when it fits in memory. Read-only helpers, images and completions still go to the small model.
- **"Reply with the single word OK." is no longer treated as vague.** The literal word "OK" counted as an unmeasurable goal, which added a workspace snapshot and an "Understood as:" preamble to plain requests.
- **Reasoning streams instead of looking stuck.** A reasoning model can think for one to two minutes before its first answer word. The reasoning used to sit in a collapsed "Thinking…" row, so the chat looked frozen. The row now opens and follows the reasoning as it streams, then folds to "Thought … Ns" when the answer starts. Reasoning written inline as `<think>…</think>` (deepseek-r1, qwen3, QwQ on servers that don't separate it) is shown the same way instead of as raw text. The status line switches to "Responding…" once the answer begins.
- **Inline completions no longer reload the chat model.** Completions didn't send a context size, so Ollama reloaded the weights every time you switched between chat and completions on the same model. They now use the same window as chat.
- **Notifications no longer cover the composer.** They sit above the composer however tall the draft, approvals or task card make it.

### Changed
- **New chats and subagents start much sooner.** Each request used to carry every installed skill's full description, about half of the prompt with ~50 skills. The skill list now shows one short line per skill in a fixed order, so a new chat's prompt is about a third smaller (≈14k → 9k tokens), and the local model reads that much less before its first word. Matching and preloading still use the full descriptions.
- **Subagents reuse the main chat's cached prompt.** A subagent's role used to replace the first line of its instructions, so the model server could reuse none of what it had already processed. Shared sections now come first and the role, memory and request-handling notes come last, so Ollama and llama.cpp only process what is new.
- **Helpers use the model already in memory when another would not fit.** Read-only subagents and the Auto-mode reviewer normally take a small model. If that model isn't loaded and wouldn't fit next to the one that is, they now use the loaded model instead of making the machine swap.
- **A calmer chat view.** Tasks and changed files now share one card above the composer instead of stacking separate boxes. When no agent is running, the task checklist folds to one line showing the current step; it opens while the agent works and remembers your choice if you toggle it. Finished tasks are muted instead of struck through, a successful `exit 0` is plain text (only failures are coloured), and file chips no longer have outlines.
- **Follow-up messages answer sooner.** The cursor position, working set and checklist used to be part of the system prompt, so every new message made Ollama re-read the whole conversation. They now travel with the newest message, so earlier turns stay identical and come from the model server's cache.
- **A clearer wait before the first word.** The status now says what is happening, updated every second: "Loading qwen3.8:27b into memory · 12s" or "qwen3.8:27b is reading the prompt (~18,400 tokens) · 4s".
- **The completion model is loaded in advance.** With inline completions on, the completion model loads at startup and when the window regains focus, instead of on the first keystroke.

## 1.0.0 — 2026-10-23

LocalPilot 1.0 — the local-first coding agent is stable: resilient model calls, a calm and steady chat, built-in skills for the whole development loop, and a release pipeline that ships every push.

### Added
